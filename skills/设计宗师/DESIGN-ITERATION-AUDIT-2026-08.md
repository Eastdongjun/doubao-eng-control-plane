# 设计宗师大版本迭代审计（2026-08）

## 结论先行

当前设计宗师的“原则覆盖面”已经很完整，但“把原则变成可执行决策”的能力仍不足。它能告诉 Agent 应该调研、比较灰阶剪影、保护 Token、检查 SVG 和做双端验证，却没有用统一的任务清单、能力路由、证据状态和阻断条件把这些动作变成必然发生的工作流。这正是出现过度规范锁定、研究缺席、审美低适配和反复调试的主要原因。

本次建议不是继续增加原则，而是增加一层轻量的执行内核：先判断任务风险与授权，再按需装载能力；每个高风险判断必须产出证据；没有证据只能标记为“未证明”，不能交付为“已完成”。

v2.0-P0 已在本地实现：能力路由、审美评估、调研覆盖、视觉值审计、SVG lint、交付门禁、任务/权威/审美/来源/资产模板和执行契约均已加入，并同步到已安装技能目录。P1/P2 也已完成实现，本文保留完整审计作为持续迭代基线。

## 关键缺口与风险

| 优先级 | 缺口 | 现象 | 根因 | 影响 |
|---|---|---|---|---|
| P0 | 能力路由不可执行 | Agent 要么把所有规范都套上，要么跳过调研和证明 | 没有任务分类、风险评分、能力清单和必需产物的机器可读契约 | 规范锁定、摸鱼、上下文浪费 |
| P0 | 审美决策不可复核 | 仍可能选择“看起来高级”的低业务适配方向 | 审美 Governor 主要是文字规则，缺少按业务权重的非补偿式评分、拒绝理由和置信度 | 审美 low、方向与业务脱节 |
| P0 | 调研没有闭环 | 能要求 live research，却没有统一的来源账本、覆盖度、停止条件和无网降级 | 研究输出格式与交付状态不统一 | 单一参考、趋势套皮、文化误读 |
| P0 | 规范治理缺少扫描器 | 文档要求 Token 只读，但无法系统发现 CSS/HTML/SVG 中的原始值、近似值和未授权变更 | 没有 authority snapshot、值分类器和 deviation ledger 的执行工具 | 设计语言漂移难以及时发现 |
| P0 | 版式与混排缺少可重复测试 | 有规则但常需多轮手工修正 | 没有真实字体/中英数标点 fixture、基线测量和间距舒适度报告 | 文字错排、基线不齐、空间秩序不稳定 |
| P0 | SVG 与配图生成缺少资产契约 | 可能得到可用但风格混杂、无来源或不可访问的资产 | 只有原则，没有 SVG lint、资产清单、生成提示词和权利状态 | 图标风格漂移、版权与无障碍风险 |
| P0 | 反摸鱼门禁不足 | Agent 可以写“已调研/已验证”，但没有代表性证明 | 质量门是叙述性的，缺少状态枚举和阻断规则 | 交付可信度下降 |
| P1 | 视觉定位图只解决锚点，不解决完整性 | 有稳定标记，但未强制检查重复、缺失、责任人和视口证据 | 脚本只解析 HTML，不校验交付包 | 局部修改仍需重新找位置 |
| P1 | 渐进式加载判定无统一输出命令 | 文档能解释原则，不能快速生成项目判定记录 | 缺少 loading manifest 和检查器 | 关键内容延迟或稳定性被破坏 |
| P1 | 参考库体量大但缺少预算 | 22 个参考文档约 21 万字符，容易被 Agent 全量加载 | 路由表没有硬性上下文预算和最小证据集 | Token 消耗增大，关键规则反而被淹没 |
| P2 | 缺少回归样本和视觉评估集 | 无法知道新版是否真的减少了荧光绿、模板化和贴边问题 | 没有跨行业、双端、普通状态的固定样本 | 迭代依赖主观感觉 |

## 建议的 v2 执行架构

### 1. 任务批次与能力路由（P0）

新增 `DESIGN_TASK.yaml` 和 `capability-router.py`。输入只要求少量事实：任务类型、是否已有规范、业务风险、视觉风险、是否需要调研、目标平台、是否产出可运行代码。路由器输出：

- `authority`: `binding-system` / `user-directed` / `research-derived` / `unresolved`
- `mode`: `conformance` / `product` / `visual` / `redesign` / `production` / `critique`
- `required_capabilities` 与 `conditional_capabilities`
- 每项能力的最小参考文件、预算和必须产物
- `blocking_gates`、`unknowns`、`evidence_status`

规则：产品/应用任务默认先业务、信息架构、状态、可用性和实现约束；纯视觉或文化任务才扩大审美研究。任何任务都保留 Token、无障碍、边界和一致性检查，但不强制加载不相关的深层参考。

### 2. 审美决策内核（P0）

新增 `AESTHETIC_DECISION_RECORD.md` 模板和评分器。每个候选方向都必须记录：

- 业务任务、受众、信任需求和情绪目标；
- 客户喜欢/拒绝的具体视觉样本与机制，而非形容词；
- 类别、谱系、邻近领域、反参考四类证据及日期；
- 2–3 个真正不同的灰阶结构（低风险合规任务可只有 1 个）；
- 按项目动态分配权重的维度：业务适配、信息清晰、品牌识别、受众文化、可访问性、可实现性、差异化、趋势半衰期；
- `fit / risk / confidence / rejection_reason`，并执行不可补偿门：业务不适配、可读性失败、文化/版权不确定、关键状态缺失时直接淘汰；
- 选择、拒绝、可混合部分、复审触发条件。

这样“好看”不再是总分，而是有业务前提的可复核裁决。评分只组织证据，不授予方向合法性。

### 3. 调研闭环（P0）

新增 `RESEARCH_BRIEF.md`、`SOURCE_LEDGER.yaml` 和 `research-coverage.py`：

1. 先写可证伪研究问题和不搜索的边界；
2. 按谱系/类别/邻近/反参考/材料与交互至少覆盖必要车道；
3. 每条来源记录 URL、日期、类型、权利、观察、推断、可转译机制和不可复制内容；
4. 输出“已改变的设计决策”和“没有改变的假设”；
5. 新来源连续不再改变语法、风险或方向空间时停止；
6. 无网时只允许使用用户提供或本地已验证资料，并明确 `research_unverified`，禁止用记忆冒充调研。

### 4. 规范权威与视觉值审计（P0）

新增 `DESIGN_AUTHORITY.yaml`、`DESIGN_VALUE_AUDIT.md` 和 `design_value_audit.py`：

- 冻结规范、Token、组件库、品牌资产的版本、所有者、优先级和例外授权人；
- 将代码中的色彩、字号、行高、间距、半径、阴影、断点、SVG 属性和动效值分类为 `token`、`semantic`、`component`、`intrinsic`、`third-party`、`legacy-drift`、`proposed`；
- 发现 15/21/23 这类近似间距、未映射颜色和未授权共享变更时阻断或进入偏差清单；
- 设计宗师只可提出 `proposed`，不能把提案写回共享 Token；
- 与 `CODE_MAP.yaml`、`CRAFT_POLICY.yaml` 对接，确保技能自身的脚本和适配器也有命名、复杂度和变更边界。

### 5. 排版、布局与创意构图验证（P0）

新增可重复 fixture 和报告，而不是继续堆叠文字规则：

- 中英数标点单位、真实 CJK/Latin fallback、数字特性、SVG 可见边界的基线样本；
- 文字角色、度量、换行、行距、字距、块间距和对齐线的测量记录；
- 图文角色、焦点区、mask/clip/position/pseudo-element 的层契约、碰撞边界和移动端变换；
- 灰阶剪影、布局指纹、首读/扫描/精读顺序和 320px/目标移动端/桌面端报告；
- 非装饰性贴边、select 内部安全内边距、横向滚动首尾和 sticky 区域纳入同一视觉 QA。

### 6. SVG 与图像生成资产管线（P0）

新增 `ASSET_BRIEF.md`、`ASSET_MANIFEST.yaml`、`svg_lint.py`：

- SVG：viewBox、可见边界、`currentColor`、描边/填充、端点/连接、光学尺寸、可访问名称、装饰隐藏和单一图标家族；
- 配图：目的、比例、焦点、裁切保护区、色彩/材质、负面约束、响应式变体、来源/生成方式、权利和替代文本；
- 生成资产必须标记 `generated-placeholder` 或 `generated-approved`，不得冒充官方品牌或真实产品截图；
- 同一项目锁定图标、插画、摄影/生成图的光线、透视、颗粒和动效语法。

### 7. 反摸鱼交付门禁（P0）

将 `quality gate` 从 prose 变成状态机：`not_started → in_progress → evidenced → approved → shipped`，另设 `blocked` 和 `unproven`。按模式给最小产物：

- `conformance`：authority snapshot、Token/value audit、deviation log；
- `product`：任务/信息架构/状态矩阵、可用性与边界证据、代表性实现；
- `visual`：taste profile、research ledger、候选剪影、Aesthetic Decision Record、代表性渲染；
- `production`：普通状态、错误/加载、双端、资产、运行日志、视觉定位图；
- `critique`：按意图排序的发现、严重度、证据和复测条件。

缺少当前验证路径必需的渲染、浏览或可安装环境能力时，必须先输出结构化授权请求；只有用户拒绝或暂缓后，才可按其接受的范围降级，并明确未证明项，不能声称完成。

## 本次迭代的明确取舍

- 不把研究、三方向和完整审美评审强加给低风险的小改动；由风险、可逆性和视觉 stakes 决定深度。
- 不把评分器变成“自动选美”；它只负责暴露证据、冲突和拒绝理由，最终裁决仍需与业务目标一致。
- 不把所有参考文档继续塞进 SKILL；核心路由保持轻量，深层知识按决策装载并有预算。
- 不把视觉定位标记、Token 名称或审计字段污染到生产 UI；它们只属于交付证据层。

## 建议的实现顺序

先做 P0 的“路由 + 证据 + 门禁”三件套，再做排版/布局和资产扫描，最后补视觉回归集。这样优先解决当前最影响交付的三类失败：没有按需加载、没有基于业务的审美裁决、没有证据却声称完成。
