# 自动编码循环

让豆包像一名结对程序员：拿到需求后，在指定项目目录里自动完成"写代码 → 运行 → 发现问题 → 自动修改 → 补注释 → 完善健壮性 → 回归验证"的闭环，直到交付"能跑且达标"的代码。

## 铁律：不碰 GUI、不抢键盘、不弹窗

- **禁止**用 AppleScript / System Events / 模拟键盘 / 模拟鼠标 操作 VSCode 或其他应用。
  这类操作是全局的、抢焦点，会打断用户正常使用电脑，且多项目时会互相干扰。
- 所有写文件、改文件、执行命令都通过**进程级通道**完成：
  1. 首选 MCP Server 工具（`mcp__vscode__dev_*`，端点 http://127.0.0.1:8848/mcp）；
  2. 备选直接使用文件系统写入（Write/Edit）与终端命令（Bash）——与 MCP 操作同一套文件系统，效果一致。
- VSCode 只是**显示层**：代码写入磁盘后，用户自己打开的 VSCode 项目会实时显示最新内容。
  需要让用户看到代码"一行一行长出来"的过程时，用 `dev_typewrite`（打字机模式）：
  先 `dev_open_file` 打开（空）文件，再 `dev_typewrite` 逐行写入（interval_ms≈150），
  全程仍是后台文件写入，不碰键盘、不抢焦点。

## 归零验收（硬性要求，交付前必过）

**"归零"= 每个进入 VSCode 的文件必须零报错、零问题**，绝不允许把有红色/黄色标记的文件留给用户。

对**每一个交付的文件**，交付前必须逐项核对：

1. **语法级归零**：代码可被编译器/解释器接受，无语法错误。
   - Python：`python3 -m py_compile <file>` 零错误；
   - JS/TS：`node --check <file>` 或 `tsc --noEmit` 零错误；
   - 其他语言同理：构建/编译必须通过。
2. **运行级归零**：可执行文件必须真实跑通（smoke test），输出符合预期。
   - 用 `dev_run_command` 在项目目录运行，exit_code=0，无未处理异常；
   - 有多个入口/参数路径的，跑代表性路径验证。
3. **Lint/类型级归零**：清除 VSCode Problems 面板可见的静态问题。
   - 未使用的 import / 变量、未定义名称、明显类型错误、行过长等，能消则消；
   - 若项目有 lint 配置（pylint / eslint / mypy 等），按其标准清零。
4. **文件级健康**：
   - 编码统一 UTF-8，中文不乱码；行尾、缩进一致；
   - 不残留临时文件、调试打印、TODO 占位导致的问题；
   - 引用的资源（依赖、图片、数据文件、相对路径）都存在。

**归零动作**：
- 发现任何问题 → 当场修复 → 重新验证，直到逐项通过；
- 修复后再整体复查一次（改一处可能影响别处）；
- 交付汇报里逐文件列出：文件、检查项、结果（语法/运行/lint 全部 ✓）。
- 用户说"归零""不能有报错""不能有问题"时，按本节对**全部**打开的项目/文件执行。

## 多项目隔离（关键约束）

- 每个任务**绑定一个项目目录**（绝对路径），所有文件路径、工作目录都基于该目录。
- 工具一律显式传 `path` / `cwd`，绝不依赖"当前窗口 / 当前焦点"——多个项目并行时天然互不干扰。
- 不同项目之间禁止交叉读写；同一文件同时只有一个任务在改。
- 任务开始前先 `dev_list_dir` 确认项目结构与既有文件，不覆盖无关内容。

## 工作流（每个任务按此闭环执行）

1. **理解需求与验收标准**
   - 提取功能点、输入输出、运行环境（语言/依赖/入口命令）。
   - 明确"什么叫通过"：能运行 + 输出符合预期 + 注释完整 + 归零（见上节）。
   - 不确定的边界条件先做合理假设并写入注释，不反问阻塞。

2. **建立闭环清单**
   - 用 TodoWrite 建立：写代码 → 运行验证 → 修复问题 → 注释完善 → 归零验收 → 交付汇报。

3. **编写代码**
   - 关键逻辑与函数写中文注释（用途、参数、返回、边界说明）。
   - 文件放在绑定的项目目录内；如需打字机展示，用 `dev_typewrite`。

4. **运行验证**
   - 用 `dev_run_command(command=..., cwd=项目目录)` 立即运行/构建。
   - 记录真实输出与退出码，作为唯一事实来源。

5. **发现问题 → 修复（循环）**
   - 报错时**先读完整错误输出**（dev_run_command 返回的 stderr / 或 dev_read_file 读文件），定位根因再修改，禁止猜。
   - 每次修改后必须重新运行，禁止"应该能跑"。
   - 修复循环上限 10 轮；超限停止，如实上报剩余问题与原因。

6. **注释与完善**
   - 运行通过后补齐：中文注释、参数校验、边界处理、错误提示。
   - 完善后再回归运行一次，确认未破坏功能。

7. **归零验收 + 交付汇报**
   - 按"归零验收"逐文件核对（语法/运行/lint 全过）后才算完成。
   - 汇报：项目目录、文件路径、运行命令、验证结果、修复过的问题清单、归零核对表、遗留事项（如有）。
   - 如需展示，用 `dev_open_project` 打开项目目录（不抢焦点地打开窗口即可）。

## 硬性规则

- 每次改动必须重跑；运行输出是唯一验收证据。
- 报错先读全文再动手，不靠猜测改代码。
- 只改绑定项目目录内的内容，不顺手改无关项目/文件。
- 涉及删除/覆盖文件时先备份或确认，不静默销毁。
- 不伪造测试结果：没跑过就是没跑过。
- 不把报错/问题文件留给用户：交付前必须归零。
- 全程后台执行，不打断用户当前操作。

## 与既有技能配合

- 根因不确定的疑难 bug → 先走 `系统化调试` 技能定位。
- 用户要求先写测试 → 走 `tdd开发` / `测试驱动开发` 技能。
- 完整软件项目（需求→上线）→ 走 `工程化总控` 技能编排，本技能负责其中的"编码开发"阶段。
- 多文件大改动 → 参考 `增量实现` 技能小步提交。
